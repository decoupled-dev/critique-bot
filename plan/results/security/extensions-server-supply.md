# Security review: extensions, crit serve, secrets at rest, supply chain

Adversarial review of branch `wip/sec-surface` (base 25f9ec0). Scope: `src/critique_bot/extensions/`,
packs loading, `server.py` / `engine/api.py` / `api_client.py`, redaction and data at rest, config
API key handling, and the release/install chain. Every confirmed finding that can be unit-tested
has a test under `tests/security/test_sec_surface_*.py` that asserts the secure behaviour and is
marked `@unittest.expectedFailure` with `# SECURITY FINDING SF-<n>`. All tests run in temporary
folders with `HOME`/`CRIT_HOME` redirected, fake secrets, fake MCP clients, and a server on
127.0.0.1 with a random port. Full suite: `Ran 2077 tests ... OK (skipped=32, expected failures=13)`.

Note for whoever fixes these: `tests/security/` sorts before `test_00_isolation.py`, so each module
imports `test_00_isolation` first to get the isolated home.

Severity uses impact × likelihood on a developer workstation: High means an attacker without the user's approval (a repository, a local user, an upstream) gets code execution or credentials. Medium means a documented control (taint, redaction, pinning, key scoping) is bypassed. Low means hard preconditions or DoS/defence-in-depth only.

## What held up

- **crit serve auth.** Every route and method needs `Authorization: Bearer`, checked with `hmac.compare_digest` before the body is read. `//v1/health`, a trailing `/`, `%68ealth`, absolute-form URIs, and `Host: evil.example` are all covered. `OPTIONS`/`HEAD` get 501 with no CORS headers, so a browser page cannot send a preflighted request, and a "simple" cross-site POST carries no token. CSRF and DNS rebinding are blocked by the token, not by Host/Origin checks (`ServerAuthHoldsTest` keeps this as a regression guard).
- **Token and server file.** Written 0600 through `O_CREAT` with mode 0600, then `os.replace`, inside a 0700 `~/.crit`. Removed on close only by the pid/port that wrote it. A non-loopback bind needs `--listen` and `--insecure`. The body is capped at 1 MiB; chunked encoding is refused.
- **Session ids and request ids.** Strict regexes (`[0-9A-Za-z][0-9A-Za-z_-]{0,63}`, hex rids), so there is no path traversal. Request ids are scoped to their session, and only one answer counts. `_check_reply` validates decisions.
- **Headless agent runs.** `agent_mode` cannot loosen the mode of an unapproved project agent. Read-only becomes ask, and unattended requests default to "no".
- **Manifests.** No shell. Placeholders must fill a whole argv element (`"--x={v}"` is a load error), `argv[0]` cannot be a parameter, NUL bytes are refused (also in nested values, which are JSON-encoded into one element), arrays and objects become one JSON element, and string values starting with `-` are refused. `handler` is limited to builtin/pack scope. Names cannot shadow built-ins or `mcp__*`, and `tool_api.merge` keeps built-ins first.
- **Packs.** Limited to the `AVAILABLE` allow-list of crit's own folders. `packs` is in `SECURITY_KEYS`, so a committed settings file cannot turn one on (outside git, see SF-3).
- **MCP transport.** `http.client` does not follow redirects or read proxy variables, so configured headers and tokens cannot be redirected to another host. Bodies are capped at 8 MB. Stdio lines are bounded by `readline(MAX_MESSAGE_BYTES)`, and server-initiated requests other than `ping` are refused, so no sampling or roots. Responses are matched by id. `readOnlyHint` is ignored; only `read_only_tools` from the config counts.
- **Project agents and commands.** Without approval they cannot loosen the mode (`effective_mode`). Writing agents are forced into a worktree, and untracked symlinks are not copied into it.
- **Data at rest.** Session events and blobs, memory.db, the audit log and agent.json transcripts are redacted on write. `.crit`, `sessions/`, `cache/` and `~/.crit` are 0700. The audit log is opened with 0600. The API key is registered with redaction and is never read from a shared or company config file.
- **Edit guard.** The model cannot write `settings.json`, extension files, `trust.json`, `mcp-lock.json`, or the config file named in settings.
- **CI.** Default `contents: read`, actions pinned by SHA, `persist-credentials: false`, no `pull_request_target`, write and OIDC permissions only on the tag-only release job, the build container pinned by digest, pip-audit and bandit gates.

## Residual risks (not filed as findings)

- **TOCTOU in the trust check.** `ExtFile.active()` hashes the file, and `load_manifest`/`load_hooks`/`load_config` reads it again. Exploiting it needs a writer racing the session start, which would also have SF-1. Fix by hashing the bytes that are then parsed.
- **Stdio MCP servers bypass the extension runner.** They start with plain `subprocess.Popen` (`mcp_client.py:179`), not `runner._popen`, so they run outside the OS sandbox that hooks and manifest tools get. They are user-approved, but SECURITY.md suggests extension programs are sandboxed.
- **`crit attach --url X` sends the local server's token to X** (`api_client.Client.from_server_file`). Harmless while servers bind loopback, but a token for one server should not be sent to another.
- **Windows `argv[0]` lookup.** On Windows, `CreateProcess` searches the current directory, and the cwd is the workspace. A bare `argv = ["git", ...]` in a hook or manifest could run `git.exe` planted in the repository. Not tested here (Linux host).
- **Sizes and output.** MCP `tools/list` (up to 50 pages of unbounded tool counts and description sizes) and hook `append_context` (8 KB each, unwrapped) go into the prompt as trusted text. The model's context can be flooded.
- **Full tool outputs.** `.crit/cache/out/*.txt` holds full tool outputs without redaction, inside the private cache folder. They are redacted when read back and sent. Reading a sensitive file asks first.
- **Shell profile edit.** `installer._posix_add_to_path` writes `export PATH="{folder}:$PATH"` without shell-escaping `CRIT_HOME`. This is only a self-inflicted risk.

## Overall assessment

The local HTTP server and the low-level primitives are careful: token auth on every path, no shell, whole-element argv, bounded transports, and redaction on write. The weak point is the **trust boundary around project content**. Approval is bound to one file's bytes, not to what it executes (SF-1, SF-2). The rule that a cloned repository cannot loosen crit depends on git, so it fails open for non-git folders and shared ancestor folders (SF-3). In the SF-3 chain, the user's API key follows the attacker's config (SF-4). Three controls that are documented as defences have bypasses: taint (SF-5), redaction (SF-6) and MCP pinning (SF-7). Fix SF-3 first, then SF-1/SF-2 and SF-4: these lead to code execution or credential leaks with no user mistake beyond running crit, or approving an extension once.

## Fix status (branch wip/fix-trust)

- **SF-3 fixed.** A project's `.crit/settings.json` values in `project_home.APPROVAL_KEYS` (`SECURITY_KEYS` plus `config`) are left out until the user approves them, git or not: `crit` asks once per content hash at start (or `crit trust .crit/settings.json`), stored in `~/.crit/trust.json` (`settings` section). An approval of `config` also hashes the named config file. An untracked root `config.json` needs the same approval. `find_bot_home` skips ancestor `.crit` folders that belong to another user or that others can write to, and stops at `$HOME` when started inside it. Values crit writes itself stay approved. Tests: `ForeignSettingsTest` (markers removed), `tests/test_project_trust.py`.
- **SF-1 fixed.** `crit trust` records, with the file's hash, a `covers` map of every project file the hook/tool/MCP file names (each string, and each word of a string, resolved against the project root and any `cwd`; files that do not exist yet are recorded as absent when the string looks like a path). `is_trusted` checks all of them, so a changed or newly appearing script turns the file off. Approvals made before this that reference project files need approval again. Not covered (documented in extending.md): modules a covered script imports, and packages fetched by `uvx`/`npx`. Tests: `TrustCoversWhatRunsTest` (marker removed), `tests/test_project_trust.py::TrustCoversWhatRunsTests`.
- **SF-2 fixed.** `_protected_paths` now also protects `.crit/hooks/` and `~/.crit/hooks/`, and every file `trust.protected_files()` lists: the `covers` of every approval in `trust.json` plus the project files named by the user's and the project's current tool, hook and MCP files. With SF-1, a write that slipped past (a command, say) still turns the approved file off. Tests: `ModelCannotWriteWhatHooksRunTest` (marker removed), `tests/test_project_trust.py::ModelCannotWriteWhatRunsTests`.
- **SF-4 fixed.** The user's key (`CRIT_API_KEY` or `local.api_key` in `~/.crit/config.json`) is attached to a config other than the user's own only when that config's url has the same origin (scheme, host, port) as one of `config.api_key_origins()`: `local.api_key_url` (saved with the key by `crit config --api-key`), the url in the user's own config (default local server when none), or `CRIT_API_KEY_URL`. `crit config --api-key-url URL` re-binds explicitly. A key written in the active config file itself is still used for that file's url. Tests: `ApiKeyBindingTest` (marker removed), `tests/test_api_key_binding.py`.
- **SF-6 fixed.** `facts.parse_text` drops every string of a `redaction.sensitive_file()` file and every literal that `facts.secret_literal` flags: redaction changes the literal itself (a known format), or redacting its source line hides it (assigned to a secret-looking name). `locate.search_strings` filters hits the same way (sensitive path or secret format) for indexes built before the fix, and `find_strings` re-checks each hit against its current source line. `find_strings` no longer echoes the query in its "no match" line. Tests: `StringsIndexTest` (marker removed), `tests/test_strings_secrets.py`.
