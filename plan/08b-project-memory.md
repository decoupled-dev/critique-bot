# Stage 8b: Project memory (the expert's "cached mental model")

## Goal
Give crit what an experienced developer has after months on a project: a compressed picture
of its structure, a sense of where changes usually land, memories of past fixes, and the
house conventions. crit builds this picture automatically, keeps it fresh, and recalls only
what a task needs. The model uses it as a hunch to verify, not as truth.

Today every session starts from zero and rebuilds its picture of the project by reading
code. The target behavior is the opposite: open the right file first, after a short check.

This stage replaces Stage 9.7 (memory proposals), which becomes the "conventions" layer below.

## Why
- **What experts actually remember** is not lines but structure, change patterns and
  episodes. The "I know where this will change" feeling is mostly experience of past changes
  matched against the new task. That is retrieval over episodes plus co-change, which the
  harness can build.
- **Memory files hurt when done naively:** in the ICLR 2026 AGENTS.md study, LLM-written files
  reduced success, and all such files added > 20% cost. Their failure modes were that they were
  generic, unverified, always injected and stale. Every design rule below answers one of those.
- **Context rot** (Chroma, NoLiMa): injecting everything hurts, so retrieve per task with a
  small budget.
- **Location vs cause** (Shi et al., Oct 2026): accurate locations mostly save tokens (up to
  39.2%), while descriptions of the bug's cause helped repair more. So episodes store the
  root cause, not just the files.
- **Structure helps mid-size models most** (LocAgent, RepoGraph, the Aider repo map). Module
  and file summaries are the "what is this for" layer on top of the Stage 8 graph.
- **Recitation and restorable compression** (Manus): memory points to sources (paths,
  commits, sessions) that the model can re-open.

## Design rules (each answers a known failure)
| Rule | Answers |
|---|---|
| Every fact has **provenance**: file+hash, commit, or session id | unverified |
| Facts tied to files are **invalidated when the file hash changes** and re-derived lazily | stale |
| **Recall per task** within a budget (default 600 tokens), never injected in full | always injected, context rot |
| Recall is labeled **"hunch: verify before relying on it"**, with confidence and sources | trusting wrong memory |
| Facts are **specific** (files, symbols, commands, causes); generic advice is rejected at write time | generic |
| Conventions need **human approval**; structure and episodes are derived automatically from code and sessions | LLM-written rules hurting |
| Memory text is **untrusted input** for taint purposes when it came from untrusted sessions (Stage 4) | poisoning |

## Memory layers
Storage: `.crit/memory/` (SQLite `memory.db` + blobs), per project; never committed
(gitignored like `sessions/`). `crit memory export/import` for sharing within a team.

### M1: Structure memory (automatic, derived from code)
- **File cards:** one or two lines per source file: purpose, main symbols, who uses it. Keyed
  by content hash.
- **Module cards:** 3–6 lines per module (Soong/Gradle/package): responsibility, entry points,
  key classes, dependencies, the test target.
- Generated **lazily**: a card is written the first time the agent reads or edits a file, or for
  files in the top-ranked Stage 8 `repo_map` of the active module. No whole-repo pass (AOSP).
- Generated by a short helper call on the local model, with the Stage 8 symbols as input (so the
  card lists real names). It is regenerated only when the hash changes, and in batches at idle times.

### M2: Change patterns (automatic, from git + sessions)
- **Co-change pairs and sets** from `git log --name-only` (Stage 8 L4), weighted by recency.
- **Change recipes** mined from repeated co-change sets plus commit messages and session episodes:
  "adding a vehicle property: `types.hal` → `VehiclePropertyIds` → `CarPropertyService` →
  `CarPropertyTest`". Each recipe lists the commits and sessions it came from.
- **Hot spots:** files with frequent fix commits (a "fix|bug|crash" subject + churn), which are
  useful priors for localization.

### M3: Episodes (automatic, from finished sessions)
Written at `task_finished` from the Stage 3 event log, after the Stage 7 flow when it ran:
```json
{
  "task": "HVAC temperature shows wrong unit after reboot",
  "class": "bugfix",
  "files_changed": ["…/HvacTemperatureHelper.java", "…/HvacPropertyTest.kt"],
  "symbols": ["HvacTemperatureHelper.toDisplayUnit"],
  "root_cause": "display unit read before the config was loaded on cold boot",
  "fix_summary": "defer unit lookup until onConfigLoaded",
  "evidence": {"repro": "passing", "tests": ["HvacPropertyTest"], "review": "no blocking findings"},
  "outcome": "verified",
  "session": "s_2026-12-03_ab12", "commit": "9f3c1e2",
  "files_hash": {"…/HvacTemperatureHelper.java": "sha256:…"}
}
```
- Only `verified` or user-accepted outcomes become trusted episodes; failed or abandoned ones
  are kept as **negative episodes** ("tried X, it was not the cause"), which feed the
  rejected-patch memory in Stage 7.
- Episodes stay valid after their files change. They describe the past, but recall marks
  them "code changed since" when hashes differ.

### M4: Conventions (proposed by the agent, approved by you; this replaces 9.7)
- At task end, the agent may propose at most 2 notes, each specific and with evidence:
  "Tests in this repo run with `atest CarServiceUnitTest`, not Gradle (session s_…, command
  output)". Generic advice ("write clean code") is rejected by a filter.
- Shown for approval in the TUI or with `crit memory review`. Approved notes go into the
  memory db (not `.crit/AGENT.md`, which stays human-written), with their evidence.
- A stale check runs weekly or on demand: a note whose evidence no longer holds (the file is
  gone, the command fails) is flagged for removal.

## Recall (the "intuition" step)
At task start, after the environment snapshot and before the first model turn:
1. **Query:** task text → keywords and symbols (Stage 8 `find_symbol` on identifiers in the
   task) + the task class.
2. **Candidates:** similar episodes (BM25 over task/root_cause/fix_summary; embeddings
   optional, via Stage 9.5), change recipes whose files match, module cards for the
   modules involved, and hot spots among them.
3. **Rank:** a score combining similarity, recency, verified outcome, co-change strength,
   and a penalty when the source files have changed since.
4. **Hunch block** (≤ budget), appended as part of the first user turn so the cached prefix
   stays stable:
   ```
   Project memory (hunch; verify before relying on it):
   - Likely files: HvacTemperatureHelper.java (0.7), HvacPropertyTest.kt (0.5)
     why: 3 past unit/display fixes touched both (episodes e14, e22, e31)
   - Similar past fix (e22, verified): cause was config read before load on cold boot
   - Module CarService/hvac: responsibility…, tests: atest CarHvacUnitTests
   Sources can be opened with memory_show <id>.
   ```
5. **Tools during the task:** `memory_search(query)`, `memory_show(id)`, and
   `memory_note(text, evidence)` (a proposal for M4). All are read-only except the proposal,
   and all are capped.

Recall can be switched off per task (`--no-memory`) or per agent (`memory: off | recall | full`).

## KV-cache priming (local models only)
llama.cpp can save and restore a slot's KV state (`--slot-save-path`, then
`POST /slots/{id}?action=save|restore`). crit can build a **project primer** (system prompt
+ tools + project memory files + the module repo map) once per project and version, save its
KV state, and restore it at session start, so starting a session costs no prompt
processing for the primer.
- The primer key is the hash of its exact bytes, model, quant and context size. Any change → rebuild.
- vLLM's automatic prefix caching gets the same effect within one server's lifetime. Preset
  docs explain both.
- This is an optimization, measured separately: time to first token at session start.

## Research option: knowledge in the weights (not in the default build)
A per-repo LoRA for the local model, trained on the repo's own history (commit diffs as
tasks, SWE-smith/SWE-Gym style), would be the deepest form of "intuition". The evidence per
repo is thin and it costs GPU time, so this is an experiment for large, stable codebases (AOSP
branches): `crit memory train --experimental`, evaluated with the same metrics below before
it is ever recommended.

## Eval protocol (does crit behave like someone who knows the project?)
- **Warm-up then test:** for each of 3 repos (crit itself, a mid-size Kotlin/Java app,
  AOSP `packages/services/Car`), run 15 warm-up tasks (which build memory), then 10 held-out
  test tasks in the same repo, with memory on and off. Run the same order 3 times.
- **Metrics:**
  - turns until the first read of a file that is finally edited
  - tokens before the first edit
  - **predicted-file accuracy:** the hunch's top-5 files against the files actually changed
  - pass@1, total tokens and wall time
  - wrong-hunch rate (top-1 file not edited) and whether a wrong hunch hurt the outcome
- **Leakage guard:** test tasks must not be duplicates of warm-up tasks (checked by diff
  overlap), so the eval measures generalization, not replay.

## Completion targets
- [ ] Memory-on vs memory-off on the held-out tasks: **turns to first correct file −40%**,
      tokens before first edit −30%, pass@1 ≥ memory-off (it must never hurt)
- [ ] Predicted-file acc@5 ≥ 60% after 15 warm-up tasks on each repo
- [ ] Wrong hunches don't reduce pass@1 (memory-on pass@1 on wrong-hunch tasks ≥ memory-off)
- [ ] Recall block ≤ budget in 100% of runs; prompt prefix stays byte-stable (the hunch is in the first user turn)
- [ ] A file change invalidates its card within one session; stale conventions are flagged
- [ ] No convention enters memory without approval (test)
- [ ] KV primer (llama.cpp): session-start time to first token −70% on a 32K primer

## Risks
- **Confident wrong hunches steer the model off course:** confidence scores, the "verify"
  label, and the wrong-hunch metric as a gate; recall is cut back automatically if the
  wrong-hunch rate on a repo goes above 50%.
- **Memory poisoning from untrusted sessions:** episodes from tainted sessions are stored
  but marked untrusted and not recalled by default.
- **Privacy:** memory holds code knowledge; it stays local, is redacted on write, and is
  excluded from exports unless asked.
- **Cold start:** new repos have no episodes. M1 cards and M2 git mining work from day one,
  so the value appears gradually instead of only after many tasks.
