# Harness quality decides what local models achieve

The literature agrees on one point: the harness matters as much as the model, and it matters most for weaker models. In the original SWE-agent ablations, interface choices alone moved results by 3 to 8 points on an 18% baseline. Factory's harness beat Claude Code by 15 points on Terminal-Bench using the same model family. Running the same model under different harnesses on Terminal-Bench 2.0 still gives gaps of about 8 points. The gains that have evidence behind them are not elaborate multi-agent designs. They are a guarded string-replace edit tool, compact and capped tool output, external verification signals (failing tests, reproduction scripts, best-of-N with hybrid selection), cheap context management (observation masking, a stable cache prefix, recitation of the plan), and structural navigation tools, which help mid-size open models more than frontier ones. For crit, which targets Qwen3.6-27B on llama.cpp or vLLM, the most valuable change is to stop writing tool calls as JSON in the reply text. Instead, use the server's native tool calling, which is the format Qwen was trained on, behind a defensive parser and per-model profiles. Make verification the default, put real OS sandboxing in place, and build replayable event-sourced sessions. Several planned features have weak support or carry real risk: WASM plugins, multi-agent writer swarms, a mandatory localization pre-pass, auto-written memory, and an interactive debugger available from turn 1. They belong at the bottom of the roadmap or off it. Most 2026 numbers for open models come from vendors and use SWE-bench Verified, which OpenAI now considers contaminated. Crit's own eval harness should therefore decide what ships, not leaderboard claims.

## Small models need the interface the 2024 papers built

SWE-agent introduced the agent-computer interface (ACI) and measured each part of it. On SWE-bench Lite with GPT-4 Turbo, the default reached 18.0%. Results fell to 10.3% with no edit command, and to 15.0% when edits were not linted. With paged, grep-like iterative search the score dropped to 12.0%, which is worse than having no search tool at all (15.7%). Showing the full file instead of a 100-line window scored 12.7%, and keeping full history instead of the last 5 observations scored 15.0% ([SWE-agent](https://arxiv.org/html/2405.15793v3)). By 2025 frontier models no longer needed most of this help. mini-SWE-agent is about 100 lines of Python with bash as its only tool, no tool-calling API and a linear history. It reaches more than 74% on SWE-bench Verified with a frontier model ([mini-SWE-agent](https://github.com/SWE-agent/mini-swe-agent)). Anthropic's 49% Verified result in January 2025 used only a prompt, bash and a `str_replace` editor that accepts exactly one match and uses absolute paths. Anthropic says it spent more effort on the tools than on the prompt ([Anthropic](https://www.anthropic.com/engineering/swe-bench-sonnet)). Taken together, these results say that **scaffold complexity matters more the weaker the model**. A harness built for 27B local models should keep the ACI guardrails while keeping the loop itself minimal.

The scaffold also matters in a second way. Every strong open-model result was run under the scaffold that model was trained on: SWE-agent-LM-32B under SWE-agent (40.2% Verified), OpenHands LM 32B under OpenHands (37.2%), and Kimi-Dev under an Agentless workflow (60.4%) ([SWE-smith](https://arxiv.org/abs/2504.21798), [OpenHands LM](https://huggingface.co/OpenHands/openhands-lm-32b-v0.1), [Kimi-Dev](https://arxiv.org/abs/2509.23045)). Qwen3.6-27B reports **77.2 on Verified, 53.5 on SWE-bench Pro and 59.3 on Terminal-Bench 2.0**. Those runs used "an internal agent scaffold with bash and file-edit tools", and the card recommends serving with vLLM's `qwen3_coder` tool parser ([Qwen3.6-27B card](https://huggingface.co/Qwen/Qwen3.6-27B)). These are vendor figures, so treat them as an upper bound. The pattern for crit is still clear. **Match the tool surface to what the model was RL-trained on**: bash plus a str_replace-style editor, called through the model's own tool-call template. A custom JSON-in-text protocol is not that surface.

Some results argue against agent loops. Agentless uses a fixed pipeline (localize, sample repairs, validate) and reached 32.0% on Lite at $0.70 per issue, which matched the agents of its time ([Agentless](https://arxiv.org/abs/2407.01489)). CodeAct found that executable-code actions beat JSON tool calls by up to 20% across 17 LLMs ([CodeAct](https://arxiv.org/abs/2402.01030)). Neither result overturns the agent loop. Agentless works when tests exist and the repository layout is predictable. Agent loops do better when the task needs exploration, building and debugging. CodeAct shows that rigid JSON is a weak point for small models. In the Nebius runs, Qwen3-Coder-30B needed its tool calls post-processed under OpenHands, while the 480B model did not ([Nebius](https://nebius.com/blog/posts/openhands-trajectories-with-qwen3-coder-480b)).

Benchmark choice now shapes what a harness builder should optimize for. In an audit of hard SWE-bench Verified tasks, OpenAI found that 59.4% had material problems, and that frontier models could reproduce gold patches verbatim. OpenAI stopped reporting Verified in February 2026 ([OpenAI](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)). SWE-bench+ found that 32.67% of "successful" SWE-agent patches leaked the solution from the issue text, and that filtering cut the resolution rate from 12.47% to 3.97% ([SWE-bench+](https://arxiv.org/abs/2410.06992)). SWE-bench Pro scored frontier models at about 23% at launch ([SWE-bench Pro](https://arxiv.org/html/2509.16941v2)), but Epoch AI rates it "Flawed" with 30% or more of tasks broken ([Epoch AI](https://epoch.ai/benchmarks/swe-bench-pro/review)). Terminal-Bench 2.0 has 89 human-verified tasks and a neutral Terminus 2 harness ([Terminal-Bench 2.0](https://arxiv.org/abs/2601.11868v1)). The same Opus model scored 74.9% under one harness and 66.5% under another ([Willison gist](https://gist.github.com/simonw/3bff274abcbbbf8766e9437a542db248)). Factory's Droid scored 58.8% against Claude Code's 43.2% on Opus ([Factory](https://factory.com/news/terminal-bench)). **These harness deltas are the number crit should compete on**: hold Qwen3.6-27B fixed and compare crit with opencode and Terminus 2.

## Execution feedback and selection drive bug-fixing gains, not reflection

Self-repair helps when it has an external signal, and much less when the model only critiques itself. Olausson et al. counted repair cost and found that self-repair gains were "often modest" and sometimes absent. They also found that spending budget on diverse first attempts beats spending it on long repair chains, and that feedback from a stronger model or a human was the real lever ([Olausson, ICLR 2024](https://arxiv.org/abs/2306.09896)). Signal quality determines how much repair helps. LDB records intermediate variable values at each basic block of a failing run and gains up to 9.8% ([LDB](https://arxiv.org/abs/2402.16906)). Failing tests with tracebacks come next, then the model explaining its own code ([Self-Debugging](https://arxiv.org/abs/2304.05128)). Pure self-critique ranks last. The harness rules that follow are simple. **Return stdout, stderr and tracebacks verbatim**. Cap repair at 2 or 3 rounds. Track patches that were plausible but rejected, so the model proposes genuinely different alternatives, as ChatRepair does ([ChatRepair](https://arxiv.org/abs/2304.00385)). Use token burn as a stop signal: RepairAgent's failed runs used about 15x the tokens of its successful ones ([RepairAgent](https://arxiv.org/abs/2403.17134v2)).

Reproduction tests are worth writing even though they are hard to get right. SWT-Bench found that keeping only patches that make a self-generated failing test pass **doubles SWE-agent's precision** ([SWT-Bench](https://arxiv.org/abs/2406.12952v2)). Yet the best fail-to-pass generation rates are only 23.6% on TDD-Bench Verified and 32.9% for Issue2Test ([TDD-Bench](https://arxiv.org/abs/2412.02883), [Issue2Test](https://arxiv.org/html/2503.16320v2)). So a repro test should be a **soft gate**. Write it first and check that it fails on the unmodified code for the reason the issue states. If it cannot be made to fail after k attempts, mark it untrusted and use it only for ranking.

Selection has become the main way to scale. In CodeMonkeys, 69.8% of Verified issues had at least one correct candidate, but random selection resolved only 45.8%. Voting with model-written tests reached 57.4% ([CodeMonkeys](https://arxiv.org/abs/2501.14723)). R2E-Gym found that test-based and judge-based verifiers each plateau at about 42 to 43%. Execution-free judges reward style, and generated tests often fail to tell candidates apart. A hybrid verifier reached **51% with an open-weight 32B agent whose pass@1 was 34.4%** ([R2E-Gym](https://arxiv.org/abs/2504.07164v1)). SWE-Gym's trained verifier added 11.4 points for a 32B model ([SWE-Gym](https://arxiv.org/html/2412.21139v2)). For a local 27B model, the best-supported way to close the gap to frontier models is to sample in parallel and pick with a hybrid verifier. The cost is real, though. CodeMonkeys spent about $4.60 per issue, and on one local GPU the extra rollouts mostly run one after another.

Localization tools help, but they do not have to run first. LocAgent's import/invoke/inherit graph gave a fine-tuned Qwen2.5-Coder-32B 92.7% file-level accuracy at 86% lower cost ([LocAgent](https://arxiv.org/abs/2503.09089)). CoSIL's on-the-fly call graphs reached about 44% function-level Top-1 with a 32B model ([CoSIL](https://arxiv.org/abs/2503.22424v2)). However, a study of 16,248 trajectories published in October 2026 found that **better fault localization did not consistently raise repair success**. Accurate locations cut repair tokens by up to 39.2%, but current FL methods often cost more tokens than they saved. Descriptions of the bug's cause helped more than bare locations ([Shi et al.](https://arxiv.org/abs/2610.25826)). Localization should therefore be a tool the agent can call, and it should report a hypothesized cause. It should not be a mandatory pre-pass.

Debuggers help only strong models with a strategy. In debug-gym, pdb raised Claude 3.7 Sonnet on SWE-bench Lite from 37.2% to 48.4%, and to 52.1% when access was delayed until after five attempts. GPT-4o dropped on the simpler Aider set (76.4 to 69.7), and Llama-3.3-70B stayed near zero. The authors say models issue pdb commands "without a clear strategy" ([debug-gym](https://arxiv.org/html/2503.21557)). For Android, deterministic triage plus logs is the strongest evidence. Removing the log agent in Holmes cut root-cause accuracy from 65.7% to 52.1% ([Holmes](https://arxiv.org/pdf/2606.21963)). "Blueprint First" runs a fixed pipeline: crash, then stack, then suspect commits. Its guard refuses to produce a draft when blame finds no candidate commit ([Blueprint First](https://arxiv.org/pdf/2508.02721)). LLM-enhanced Java crash reports raised Top-1 localization from 10.6% to about 40% ([Crash Report Enhancement](https://arxiv.org/abs/2509.13535v1)). No benchmark covers native, HAL or SELinux debugging on AOSP. That is both a gap in the research and an opening for crit.

## One writer, adaptive plans, read-only helpers

Planning helps when it adapts to failure and is grounded in the code. Rigid planning does not help in the same way. ADaPT decomposes a task only when the executor fails, and gained up to 28 to 33% on interactive benchmarks ([ADaPT](https://arxiv.org/abs/2311.05772)). CodePlan pairs adaptive planning with dependency and may-impact analysis after each edit. It passed validity checks on **5 of 6 repo-wide migrations, against 0 for baselines with the same context but no planning** ([CodePlan](https://arxiv.org/abs/2309.12499)). Static plan-then-execute designs such as ReWOO and LLMCompiler mostly save tokens and latency ([LLMCompiler](https://arxiv.org/abs/2312.04511)). In coding, that value comes from running independent reads in parallel. No controlled study of plan mode on SWE-bench was found. Cursor says plan mode "significantly improve[s]" the code it produces but gives no numbers ([Cursor](https://cursor.com/blog/plan-mode)). OpenAI's Codex guide warns that up-front plan instructions caused early stopping on older models ([Codex guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide)). The design that best fits the evidence is a ReAct core, plan mode suggested when a task looks complex or an attempt fails, and a deterministic impact step that pushes affected call sites onto the todo list.

Multi-agent setups help with reading and hurt when agents write code that depends on each other. MAST annotated more than 1,600 traces and found 14 failure modes. Its authors conclude that multi-agent gains on popular benchmarks "are often minimal" ([MAST](https://arxiv.org/abs/2503.13657)). A strong single agent can simulate homogeneous workflows, and KV-cache reuse makes it cheaper ([Rethinking MAS](https://arxiv.org/abs/2601.12307)). In CooperBench, paired coding agents succeed about **30% less often** than one agent doing both tasks ([CooperBench](https://arxiv.org/abs/2601.13295)). Cognition's rules are to share full traces and to remember that actions carry implicit decisions ([Cognition](https://cognition.com/blog/dont-build-multi-agents)). Anthropic reports a 90.2% gain from multi-agent research, but says the approach is a poor fit for "most coding tasks", and that multi-agent setups use about 15x the tokens of chat ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). Three multi-agent patterns hold up in coding. The first is read-only exploration in a fresh context that returns a summary of 1,000 to 2,000 tokens ([Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). The second is an independent tester or reviewer that cannot see the author's reasoning ([AgentCoder](https://arxiv.org/abs/2312.13010)). The third is a split between different models: Aider's architect/editor pairing improved every pair tested, including GPT-4o-mini paired with itself, which rose from 55.6% to 60.2% ([Aider architect](https://aider.chat/2024/09/26/architect.html)).

Production tools have settled on the same design. Claude Code, opencode and Cline each run one primary agent that does all the writes. Plan mode is a permission profile the harness enforces: reads, plus writes to the plan file, plus an approval exit. Subagents are declarative files with tool allowlists, a model, a step cap, depth and concurrency limits, optional worktree isolation, and summary-only returns ([Claude Code sub-agents](https://code.claude.com/docs/en/sub-agents), [opencode agents](https://opencode.ai/docs/agents/), [Cline](https://docs.cline.bot/core-workflows/plan-and-act)). opencode removes tools on the last allowed step so the model is forced to summarize. The OpenAI Agents SDK separates an agent called as a tool, which returns a result, from a handoff, which passes over the conversation ([handoffs](https://openai.github.io/openai-agents-python/handoffs/)). Crit's `delegate` tool, plan review and roles already follow most of this design. What remains is to enforce plan mode through permissions rather than the prompt, add worktree isolation for any subagent that can write, and give each delegation a template: objective, output format, tools and scope.

## Context is a budget of 16-32K tokens behind a cache that must stay intact

Advertised context overstates usable context. Chroma tested 18 models, including Qwen3-32B and Qwen3-8B. All of them degraded as input grew, even on simple tasks, and focused inputs of about 300 tokens beat full inputs of 113K tokens for every model ([Chroma](https://www.trychroma.com/research/context-rot)). In NoLiMa, 10 of 12 models with claimed windows of 128K or more fell to half their short-context score by 32K ([NoLiMa](https://arxiv.org/abs/2502.05167)). RULER rates Qwen2-72B as effective to 32K of a claimed 128K ([RULER](https://github.com/nvidia/RULER)). Qwen3.6-27B claims 262K native context, but no independent effective-context measurement was found. Practitioners serving it locally often run 16 to 64K ([DEV guide](https://dev.to/purpledoubled/how-to-run-qwen36-27b-locally-the-dense-27b-that-beats-the-35b-moe-on-coding-172e)). Crit's compaction thresholds and output caps should therefore **scale with the configured and measured effective window, not the model's maximum**. Logs, build output and logcat contain many similar lines that act as distractors, which is exactly the case Chroma found most damaging. Filter them before they reach the model. Crit's log tool already does this.

The cheap compaction methods do as well as the expensive ones. JetBrains' "Complexity Trap" study ran SWE-agent on all 500 Verified instances. Observation masking, which keeps the last 10 observations and elides older ones, halved cost and matched LLM summarization. Summaries also hid failure signals, which made runs about 15% longer ([Complexity Trap](https://arxiv.org/html/2508.21433v3)). Qwen3-32B is the exception that matters for crit. In non-thinking mode, masking cost 2 points (17.0% to 15.0%). In thinking mode, masking and summarization both helped slightly (23.0% to 24.6% and 24.8%). A hybrid that masks routinely and summarizes rarely gained 2.6 points and was the cheapest option. Anthropic calls tool-result clearing the "lightest touch" form of compaction. Claude Code's summary keeps decisions, open bugs and implementation details, and then re-attaches the five most recently accessed files ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Manus adds three practices: keep compression restorable (drop the content but keep the path or URL), keep errors in context, and rewrite a `todo.md` so the goals sit at the end of the context ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)). For very long tasks, Anthropic found compaction was not enough. Its fix was an initializer that writes a JSON feature list, which models corrupt less often than Markdown, plus a progress file, git commits and one feature per session ([Anthropic long-running](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).

Prompt caching decides whether a local agent feels fast. Manus reports a 100:1 ratio of input to output tokens and calls KV-cache hit rate "the most important metric." Codex keeps the tool list, sandbox message and cwd byte-stable, and it records any change as an appended message. An MCP bug that returned tools in unstable order caused cache misses ([Codex loop](https://openai.com/index/unrolling-the-codex-agent-loop/)). vLLM matches prefixes only from the start of the prompt, in 16-token blocks ([vLLM](https://docs.vllm.ai/en/latest/design/v1/prefix_caching/)). llama.cpp chooses a slot by similarity, so pin `id_slot` to keep each session on its own cached prefix ([llama.cpp #13606](https://github.com/ggml-org/llama.cpp/discussions/13606)). Every masking pass or summary rewrites the middle of the history and forces a full re-prefill from that point on. Crit's compaction triggers based on turns and time should therefore give way to **rare, batched compaction events at turn boundaries**, triggered by measured context pressure. The prompt order should be fixed: system prompt, tools in a fixed order, AGENTS.md, then the repo map, followed by append-only turns. Date and git status belong in the first user turn.

Memory files have the weakest evidence of anything crit already ships. An ICLR 2026 study found that AGENTS.md files generated by an LLM **tend to reduce** success, files written by developers help only slightly, and both raise inference cost by more than 20% ([Evaluating AGENTS.md](https://arxiv.org/abs/2602.11988)). Keep `.crit/AGENT.md` short and written by people. Load AGENTS.md hierarchically from the repo root down to the cwd, as Codex does with its 32 KiB cap ([Codex guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide)). Do not auto-generate these files by default.

On retrieval, the evidence supports agentic search as the default, with structure added on top. Claude Code dropped vector RAG for glob and grep ([Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/building-claude-code-with-boris-cherny?open=false)). Cline refuses to index codebases at all ([Cline](https://cline.bot/blog/why-cline-doesnt-index-your-codebase-and-why-thats-a-good-thing)). Aider sends a tree-sitter map of definitions and references, ranked over the file dependency graph, within a 1K-token default budget ([Aider repo map](https://aider.chat/docs/repomap.html)). RepoGraph's line-level graph improved all four agent systems it was added to ([RepoGraph](https://arxiv.org/abs/2410.14684)). Cursor's A/B tests show semantic search adding **12.5% accuracy on average, and 2.6% better code retention on repos with 1,000 or more files**, but only when combined with grep ([Cursor](https://cursor.com/blog/semsearch)). These are vendor numbers without sample sizes. For AOSP, the research suggests scoping maps to each module, returning paths and line numbers before content, and treating embeddings as optional. No AOSP-scale evaluation of any of these methods exists.

## Native tool calls, forgiving edits, real sandboxes

Crit's choice of edit format is sound. Its tool protocol is not. The formats that work share four traits: no line numbers, explicit old and new text, clear delimiters, and lenient application. Aider found that **removing flexible patching raised edit errors 9x** ([Aider udiff](https://aider.chat/docs/unified-diffs.html)). OpenAI's GPT-4.1 guide reaches the same conclusion about delimited formats ([GPT-4.1 guide](https://developers.openai.com/cookbook/examples/gpt4-1_prompting_guide)). opencode sends `patch` to GPT models and `edit`/`write` to everything else ([opencode tools](https://opencode.ai/docs/tools/)). Factory uses edit formats and path conventions chosen per model ([Factory](https://factory.com/news/terminal-bench)). On Aider's leaderboard, Qwen3-32B produced well-formed diffs 83.6% of the time and QwQ-32B 67.6%, while whole-file output was 99.6% well-formed ([Aider leaderboard](https://aider.chat/docs/leaderboards/)). That gap justifies an automatic fallback to whole-file writes after repeated edit failures. On protocol, OpenAI measured a **+2% gain on Verified just from passing tools through the API `tools` field** instead of the prompt ([GPT-4.1 guide](https://developers.openai.com/cookbook/examples/gpt4-1_prompting_guide)). For Qwen, the native path is its own XML-style `<function=...><parameter=...>` template. Inside that template, code arguments need no JSON escaping, unlike crit's current scheme of JSON in the reply text.

The local serving stack is where tool calling breaks. llama.cpp needs `--jinja` and a template it recognizes, and it warns that aggressive KV quantization such as `q4_0` "can significantly degrade tool-calling performance" ([llama.cpp function calling](https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md)). In llama.cpp #19382, Qwen3-Coder under opencode emitted duplicate `filePath` parameters. The streaming parser corrupted them, and opencode retried the same malformed call without end ([llama.cpp #19382](https://github.com/ggml-org/llama.cpp/issues/19382)). Other reports describe calls landing in `reasoning_content` ([#20809](https://github.com/ggml-org/llama.cpp/issues/20809)). The design that follows has three parts. Use native calling as the primary path, with tested launch presets for each server. Back it with a fallback parser that accepts calls found in `content` or `reasoning_content` as Hermes JSON, Qwen XML or fenced JSON, repairs and schema-validates the arguments, and returns schema errors to the model as tool results. Stop retrying a call that is identical and malformed, and offer a non-streaming fallback. Monitor-guided decoding supports constrained decoding in general ([MGD](https://arxiv.org/abs/2306.10763)). No study measured the effect of GBNF or JSON-schema constraints on agentic tool accuracy, so apply them only inside the call span and keep reasoning unconstrained.

Tool descriptions and output shaping are also measurable levers. Anthropic reports that small description edits produced state-of-the-art SWE-bench results, and that a concise response mode cut tokens to about a third (72 against 206). Its guidance is to consolidate workflows rather than wrap endpoints, use namespaced names, and write errors that steer the model ([Anthropic tools](https://www.anthropic.com/engineering/writing-tools-for-agents)). Codex caps tool output at about 10K tokens, keeping the head and tail, which suits local windows better than Claude Code's 25K. Factory found that **short default shell timeouts improved average performance**, along with a background-process registry and an environment bootstrap shown as shell output ([Factory](https://factory.com/news/terminal-bench)). On diagnostics, the SWE-agent lint guardrail is worth 3 points. opencode, by contrast, now ships LSP **disabled by default**, warning that it drifts out of sync, uses significant memory and slows work ([opencode LSP](https://opencode.ai/docs/lsp/)). The pragmatic pipeline is a tree-sitter parse check on every edit, followed by a time-bounded fast linter or typechecker on the changed files. It should report only new errors in the changed region, and LSP should be opt-in. Full jdtls or clangd over AOSP is impractical.

Security is where crit can most clearly beat opencode. opencode's shell "runs with the host user's full authority" and allows almost everything by default ([opencode permissions](https://opencode.ai/docs/permissions/)). Anthropic's bubblewrap/seatbelt sandbox allows writes only inside the workspace and sends network traffic through an allow-listing proxy. It **cut permission prompts by 84%**, and it is open source as `sandbox-runtime` ([Anthropic sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)). Codex ships read-only, workspace-write and full-access modes ([Codex](https://github.com/openai/codex)). Willison's lethal trifecta is private data, untrusted content and an exfiltration channel. A 95% guardrail is a failing grade against it, so once untrusted content enters the context, the agent's ability to act should be restricted ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). That bears directly on crit's "auto = full control" direction. MCP has the same problem. Tool-description poisoning and rug pulls are documented attacks ([Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification)), and MCP outputs are an injection vector too ([CyberArk](https://www.cyberark.com/resources/home/poison-everywhere-no-output-from-your-mcp-server-is-safe)). An MCP client therefore needs four things: hash-pinned descriptions with diffs shown when they change, full arguments in approval prompts, output labeled as untrusted, and schemas loaded only when needed. ACP is newline-delimited JSON-RPC over stdio, and crit already has it. It gets crit into Zed and other ACP clients at little cost ([ACP](https://agentclientprotocol.com)).

## Roadmap: protocol and sandbox first, verification second, scale third

**First, make local Qwen reliable and safe.** This phase targets the measured failure points: tool-call formatting, edit application, context pressure and host authority. Add native function calling through the OpenAI-compatible `tools` field in the models layer. Keep a tolerant fallback parser and retry breaker, and keep the current text protocol as one profile option. Add per-model and per-server profiles holding sampling defaults from the model card, the tool parser, `preserve_thinking`, the edit format, the effective context budget, and output caps scaled to that budget (about 10K head and tail at most, lower at 32K). Harden `edit` with the fuzzy-match ladder, a tree-sitter parse guard and a time-bounded linter that reports only new errors, with automatic whole-file fallback after repeated failures. Rework compaction so it triggers on measured context pressure. Mask old observations in batches, summarize rarely, re-attach recently read files, and order the prompt for the cache, with dynamic state moved to the first user turn. Pin the llama.cpp slot. Ship a bubblewrap/Landlock sandbox that allows writes only in the workspace, with egress through crit's existing allow-list acting as a proxy, and prompts only for escapes. Add taint tracking so that "auto" mode loses egress and push rights once untrusted content enters the context. Make the session store an append-only event log from day one, since resume, fork, audit and eval replay all depend on it. Extend the eval runner to report pass@1, pass^3, tokens, wall time, tool error rate and malformed-call rate, with trials isolated in worktrees. Then run it on Qwen3.6-27B against opencode on the same server. Every later decision depends on that baseline.

**Second, verify by default and open the tool boundary carefully.** Build the repro → fix → test → review flow as crit's default for bug-fix tasks. The repro gate should be soft. Keep a memory of rejected patches, stop early when tests show no progress, and give the reviewer test evidence (ideally a different model). The existing code-review mode is a natural home for that reviewer. Add plan-mode triggers based on complexity and failure, plus impact analysis that pushes call sites onto the todo list. Generalize roles into file-defined agents with tools, model, permission profile, steps, depth and concurrency caps, worktree isolation for writers, and summary returns. Build the HTTP server split with an OpenAPI-first API, so headless agents, the job queue, ACP and the web UI share one engine. Add manifest command tools, which run inside the sandbox, and an MCP client with hash-pinned descriptions, deferred schemas and untrusted-output labels. Start indexing v1: lexical search plus tree-sitter symbols, and "who calls / defines / imports" graph tools scoped per AOSP module, layered on crit's existing catalog. Add git blame and log tools, and an audit log for egress.

**Third, scale and differentiate.** Add opt-in best-of-N worktree attempts with hybrid selection (tests, behavioral clustering, judge tie-break) and a cost meter. Add SCIP or compile_commands cross-references and signed, revision-pinned shareable indexes for AOSP, plus optional local embeddings for large trees. Build an AOSP domain pack: logcat, tombstone and ANR triage pipelines with a refusal guard, Soong module awareness, and adb or device-in-the-loop test tools. Build a gated, batch-mode DAP/gdb tool. Add budgets and an architect/editor cascade. Add Python plugins behind hooks. Add provenance-tracked memory proposals that require human approval. Build an AOSP task suite, since no public benchmark covers this domain and crit can define one.

**What not to build.** Skip the WASM plugin runtime. Skip writer swarms of role-play agents (PM/architect/engineer) or Bedrock-style chains in which several agents write the same code. Skip a mandatory fault-localization pre-pass and a whole-tree repo map for AOSP. Do not auto-generate AGENTS.md or auto-inject agent-written memory. Do not run full LSP over AOSP by default. Do not compact on a timer or refresh the repo map every turn, because both rebuild the cache. Do not offer an interactive step-by-step debugger from turn 1. Do not make V4A `apply_patch` the default for Qwen. Do not use a separate apply model as the main edit path, since Cognition found 2024-era apply models fragile ([Cognition](https://cognition.com/blog/dont-build-multi-agents)). Do not chase a SWE-bench Verified headline.

## Conclusion

The research points crit toward a specific kind of competitive position. opencode is broad, and matching its breadth will not beat it. It can be beaten on three narrower points the literature measures directly: local tool-call reliability, verification, and safety. Each is large in effect and cheap to build compared with an indexing engine or an agent platform. Crit's text protocol was a reasonable workaround when servers lacked solid parsers. Since Qwen3.6 is now trained and evaluated on its own call template, the protocol has become a cost, and swapping it out is probably the largest single gain available for the least effort. An event-sourced core turns several separate wishlist items into one: resume, fork, audit, replay-based evals and parallel attempts all come from the same log.

The research is least reliable where crit's ambitions are greatest. There are no AOSP-scale localization benchmarks, no gdb-agent studies, no rigorous evaluation of auto-memory, and no independent numbers for Qwen3.6 under a common scaffold. That gap cuts both ways. Claims about the indexing engine and domain packs cannot yet be backed by citations, so crit's own eval harness has to produce the evidence. Whoever builds the first credible AOSP agent benchmark will also set the terms for comparing agents in that domain.
